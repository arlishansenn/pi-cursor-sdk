# Research: Open-source alternatives to Parallels for the Windows platform-smoke lane

## Summary

On this Apple Silicon Mac (macOS 26.6.2), Apple’s Virtualization.framework still does not document a Windows guest, and Tart cannot run Windows because it only wraps that framework. The only OSI-licensed local hypervisor that officially supports a Windows 11 Arm guest on Apple Silicon today is Oracle VirtualBox 7.2+ (GPLv3 base package; macOS 26 Tahoe is a supported host). It is not a drop-in for Crabbox’s `--provider parallels` linked-clone lane, and no single official document shows the full QEMU combo (qcow2 `savevm`/`loadvm` + Windows 11 Arm + guest agent IP + `-display none`). Recommendation: do not adopt a local open-source stack for `smoke:platform:all` yet. If the Windows lane must leave Parallels without buying it, point the existing SSH provider at a real Windows host or a public-repo `windows-latest` job (Windows Server 2025 x64, not Windows 11 Arm). Otherwise keep the prior Fusion Pro route.

## Findings

1. **Apple Virtualization.framework does not support Windows 11 Arm, including on macOS 26.** The current framework overview says it is for “macOS or Linux-based operating systems” only. Topics list macOS and Linux guests; there is no Windows guide. WWDC22 (“Create macOS or Linux virtual machines”) is the same scope. https://developer.apple.com/documentation/virtualization https://developer.apple.com/videos/play/wwdc2022/10002/

2. **Tart is not an open-source Windows path.** Current README: “macOS and Linux virtual machines (VMs) on Apple Silicon” using `Virtualization.Framework`. Issue #1123 is open, labeled “not possible atm.” Maintainer (2025-09-15): Windows support needs either Virtualization.framework devices or Windows drivers for Apple Silicon virtualization; QEMU’s working path uses Hypervisor.framework, which Tart would have to implement itself. License at `main` is Functional Source License 1.1 with an Apache-2.0 future grant after two years (copyright 2022–2026 OpenAI). FSL is not OSI open source: competing commercial use is excluded until the future grant. `tart ip` and `--no-graphics` exist, but only for macOS/Linux guests. https://raw.githubusercontent.com/cirruslabs/tart/main/README.md https://github.com/cirruslabs/tart/issues/1123 https://raw.githubusercontent.com/cirruslabs/tart/main/LICENSE https://tart.run/faq/

3. **Other Virtualization.framework CLIs do not change this.** Apple’s own samples are macOS and Linux only. Projects that advertise Windows on Apple Silicon (for example MacDow) put Windows on QEMU/HVF and keep Virtualization.framework for macOS. No maintained vz CLI with substantial docs exposes a Windows guest, because the framework does not.

4. **QEMU pieces exist separately; the combined Windows 11 Arm smoke recipe is not an official documented case.** Official disk-image docs: VM snapshots (`savevm`/`loadvm`) need a writable non-removable qcow2 disk; state lives in that image; known limits are removable devices and incomplete USB snapshot support. They do not name Windows. Guest agent `guest-network-get-interfaces` (since 1.1) returns guest IPs and is built when `CONFIG_WIN32 or HAVE_GETIFADDRS`. `-display none` means “Do not display video output”; `-accel` lists `hvf` as an architecture-dependent accelerator, not as a Windows-on-macOS recipe. virtio-win publishes a community Windows-on-Arm QEMU guide (not QEMU upstream). A 2021 QEMU GitLab issue recorded HVF failing to boot Windows 11 Arm; that is a bug report, not a supported matrix. https://qemu.readthedocs.io/en/master/system/images.html https://www.qemu.org/docs/master/interop/qemu-ga-ref.html https://www.qemu.org/docs/master/system/invocation.html https://github.com/virtio-win/virtio-win.github.io/blob/main/Knowledge-Base/Windows-arm64-vm-using-qemu.md

5. **VirtualBox 7.2 is the open-source local candidate, with caveats the 7.1 note missed.** Current manual (copyright through 2025, publisher line August 2025 in the installation topic): Apple Silicon hosts include “26 (Tahoe)”. Host/guest matrix: Arm64 macOS host → Arm64 guest → Linux and **Windows 11**. Arm64 guest table: “Windows 11 (64-bit). Released versions only.” with “Premier (macOS hosts only)”. 7.2 release notes: “This release adds the ability to install Windows 11 as a guest OS on a VM with a virtual Arm processor. Guest additions are available. The Arm64 host can be running either macOS or Windows 11 (Experimental Feature).” Arm host limits that still apply: Arm guests only (no x86 guests), VMSVGA only, no unattended install, no TPM/chipset/nested-virt UI settings. Base platform package is GPLv3; Extension Pack is a separate license and is not required for headless NAT + Guest Additions. Linked clones exist (`VBoxManage clonevm`, differencing disks; GUI clone requires the source VM not running). Snapshots exist, but the manual does not document Parallels-style “linked clone from an explicit powered-off snapshot” as a one-flag operation. `VBoxHeadless` / `startvm --type headless` is the headless path. https://www.virtualbox.org/manual/UserManual.html https://www.virtualbox.org/manual/topics/installation.html https://docs.oracle.com/en/virtualization/virtualbox/7.2/relnotes/relnotes-rn-features.html https://www.virtualbox.org/manual/topics/working-with-vms.html

6. **UTM, Lima, and Multipass still do not replace this lane.** Prior evidence still holds: UTM (Apache-2.0 app around QEMU) can boot Windows Arm but has no snapshot verb in `utmctl`; Multipass is Ubuntu-only; Lima is Linux VMs. No 2026 primary doc reviewed here adds Windows snapshot/clone parity. See `docs/evidence/hypervisor-alternatives-platform-smoke-2026-09-30.md`.

7. **GitHub Actions `windows-latest` is a real Windows VM, but not Windows 11 Arm, and it does not preserve the local Crabbox lane.** Docs: public standard runners are free and unlimited; private standard runners consume included minutes then bill. Public `windows-latest` is Windows x64, 4 vCPU / 16 GB, image README is Windows Server 2025 (10.0.26100). Private `windows-latest` is 2 vCPU / 8 GB x64. Windows Arm is a different label, `windows-11-arm`, not `windows-latest`. Standard Windows rate is $0.010/minute for both `actions_windows` and `actions_windows_arm` (larger runners are not free on public repos). Windows runners run as administrators with UAC disabled. Default shell is `pwsh`. ConPTY is a Windows console API, not something GitHub documents as a runner feature; a job can start a ConPTY child, but that is not the same evidence path as Crabbox SSH capture. https://docs.github.com/en/actions/reference/runners/github-hosted-runners https://docs.github.com/en/billing/managing-billing-for-github-actions/about-billing-for-github-actions https://docs.github.com/en/billing/reference/actions-runner-pricing https://raw.githubusercontent.com/actions/runner-images/main/images/windows/Windows2025-Readme.md https://docs.github.com/actions/reference/workflow-syntax-for-github-actions

8. **SSH-remote Windows reuses the macOS pattern; it does not fit in the current Windows branch.** `buildTargetBaseArgs("windows-native")` always emits `--provider parallels` plus `--parallels-source`, `--parallels-source-snapshot`, `--parallels-user`, `--parallels-work-root`. macOS already uses `--provider ssh` with static host/user/port/work root. Doctor requires the `parallels` provider in the registry and runs a Parallels doctor; SSH doctor + `ssh BatchMode` probe are macOS-only and check Unix tools (`rsync`, `tar`), not Windows OpenSSH/ConPTY. The lock test in `test/platform-smoke-artifact-transport.test.ts` asserts `--parallels-source` = `pi-extension-windows-template` and snapshot `crabbox-ready`. Docs table in `docs/platform-smoke.md` says windows-native is `parallels`. A remote Windows lane is a small, explicit change set: `crabbox-runner.mjs`, `doctor.mjs`, `platform-smoke.config.mjs`, that test, and `docs/platform-smoke.md`. It still needs a Windows OpenSSH host with Node and a stable work root. Crabbox itself has no `virtualbox` or `qemu` provider (prior evidence: providers are `local-container`, `apple-container`, `apple-vm` Linux-only, `multipass`, `tart` macOS VMs, `hyperv` on Windows hosts).

9. **Windows guest licensing has no extra official “automate this eval” path beyond the 90-day Enterprise eval.** Evaluation Center: register, download, and install “full-featured software for a 90-day evaluation”; product key not required; expiry goes non-genuine and the PC shuts down every hour. US eval page lists Windows 11 Enterprise 26H2 as x64 and Arm64 ISO, plus LTSC 2024 x64. The page does not say the eval may be snapshotted for CI or used in production. Windows on Arm FAQ only documents Azure and Hyper-V on a Windows on Arm device for Arm VMs, not Mac hypervisors. Virtual-desktop licensing guidance is for Commercial Licensing customers, not a free dev/test grant. GitHub-hosted runners avoid shipping an ISO; the OS license is GitHub’s. https://www.microsoft.com/en-us/evalcenter/evaluate-windows-11-enterprise https://www.microsoft.com/en-gb/evalcenter/download-windows-11-enterprise https://learn.microsoft.com/en-us/windows/arm/faq https://www.microsoft.com/licensing/guidance/Windows-11-Licensing-for-Virtual-Desktops

## Recommendation

Keep the Windows lane off a local “open source Virtualization.framework” stack. That path does not exist on macOS 26.

- If the goal is a local OSI hypervisor: VirtualBox 7.2 is the only one whose own manual lists Windows 11 on Apple Silicon. Treat it as a prototype, not a Parallels replacement, until a Crabbox provider can linked-clone from a powered-off snapshot, read an IP, and SSH in headless. Guest OS is still a 90-day eval unless you buy a real license.
- If the goal is to stop paying for Parallels and still run something like today’s gate: add an SSH Windows target (or run the Windows suites on `windows-latest` in CI). SSH matches the macOS lane and is the smaller code change. `windows-latest` is free on the public upstream/fork and is real Windows, but it is Server 2025 x64, ephemeral, and outside `npm run smoke:platform:all`.
- If the goal is the closest local equivalent with the least product risk: stay on the Fusion Pro route from the previous note. It is not open source.

## Gaps

- No Apple doc was found that adds Windows guests in macOS 26.x point releases. Absence is from the current framework landing page and WWDC scope, not a line-by-line audit of every macOS 26 release note.
- QEMU has no upstream page that certifies Windows 11 Arm + HVF + internal snapshot + qemu-ga together on macOS.
- VirtualBox linked-clone behavior on an Arm Windows guest with Guest Additions IP reporting was not executed (research-only). The manual also does not spell `startvm --type headless` in the page fetched for clones; headless is documented as `VBoxHeadless` elsewhere.
- FSL competing-use edge cases (internal CI vs offering Tart as a service) were not legally interpreted beyond the license text.
- GitHub does not document ConPTY. Whether a `windows-latest` job can satisfy this repo’s ConPTY evidence contract is an implementation question, not a runner-image fact.
- Microsoft eval pages do not state a CI/snapshot exception. Do not treat the 90-day ISO as an unlimited automated lab license.
